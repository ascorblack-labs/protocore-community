# Поверхность инструментов

> Аудитория: инженер, который добавляет инструменты, доступные агенту, в
> **чистом ядре** (`protocore/`), или рассуждает о них.
> Область: текущая библиотека ядра (`protocore/`). Ядро владеет
> *контрактами, именами, диспетчеризацией, гейтингом, извлечением и порядком*
> инструментов. Оно поставляет несколько конкретных инструментов, вся
> поверхность которых **является** контрактом протокола, — ask-user
> (`tools/ask_user.py`) и память (`tools/memory.py`), — но **не** регистрирует
> ни одного конкретного
> *постного инструмента по умолчанию* (sandbox / exec / read / write); эти
> продакшен-инструменты, привязанные к бэкенду, живут в соседнем корпоративном
> репозитории. (**Контракт** `IWorkspace` живёт в ядре, но его конкретные
> инструменты — только в хосте; см. подсистему рабочего пространства в
> [`architecture.md`](architecture.md).)
> Более широкую картину см. в [`architecture.md`](architecture.md).

Ядро намеренно держит список инструментов, видимых агенту, **маленьким и
стабильным**: небольшой универсальный пул делает промпт дешёвым для меньших
локальных моделей, а детерминированный порядок сохраняет переиспользуемость
KV-prefix-кэша между ходами. Для поверхности *постных значений по умолчанию*
(sandbox / exec / read / write) ядро не регистрирует ни одного конкретного
инструмента — оно определяет *форму* и механику, которая безопасно выполняет
один вызов инструмента, а хост привязывает реализации, обеспеченные
бэкендом. (Ядро всё же поставляет собственные инструменты поверхности протокола —
ask-user и память, — см. [замечание об области](#поверхность-инструментов)
выше.)

## Постная поверхность из 7 глаголов

`contracts/lean_tool_surface.py` определяет канонический пул из **ровно семи
глаголов**. Способная модель вручную компонует операции против среды выполнения
вместо заполнения дюжины узкоспециализированных типизированных схем. Имена —
стабильные, доменно-нейтральные идентификаторы, которые бэкенд ДОЛЖЕН перенимать
дословно, чтобы поверхность, видимая агенту, была единообразной между бэкендами.

Константы `LEAN_TOOL_EXEC`, `LEAN_TOOL_READ`, `LEAN_TOOL_READ_SILENT`,
`LEAN_TOOL_WRITE`, `LEAN_TOOL_FIND`, `LEAN_TOOL_SEARCH`, `LEAN_TOOL_ANSWER`
собираются в упорядоченный кортеж `LEAN_TOOL_NAMES`:

| Глагол | Константа | Что делает |
|---|---|---|
| `exec` | `LEAN_TOOL_EXEC` | Запускает зарегистрированный бинарник среды выполнения по пути со списком argv и опциональным stdin (`{path, args, stdin}`). Это **не** `/bin/sh` — обработки метасимволов оболочки нет. Единственный мощный инструмент, позволяющий одной способной модели вызвать любой бинарник среды выполнения без отдельного типизированного глагола на каждую операцию. |
| `read` | `LEAN_TOOL_READ` | Читает файл/запись **и фиксирует её путь как наблюдённое свидетельство** (отслеживается для grounding). Используйте для любого источника, на который вы можете сослаться. |
| `read_silent` | `LEAN_TOOL_READ_SILENT` | Читает файл/запись **без** фиксации её как свидетельства. Содержимое идентично `read`; различается лишь побочный эффект для grounding. Позволяет модели просматривать или сравнивать кандидатов, не засоряя набор цитирований. |
| `write` | `LEAN_TOOL_WRITE` | Создаёт или изменяет файл/запись (глагол мутации). Бэкенды с оптимистичной записью могут принимать хеш содержимого для compare-and-swap — это забота бэкенда, а не часть универсального имени. |
| `find` | `LEAN_TOOL_FIND` | Находит файлы/записи по шаблону имени или пути (обнаружение на уровне имени файла). |
| `search` | `LEAN_TOOL_SEARCH` | Ищет по *содержимому* файлов/записей по запросу (обнаружение на уровне содержимого). |
| `answer` | `LEAN_TOOL_ANSWER` | Выдаёт финальный, терминальный ответ для задачи с подтверждающими цитированиями (`{message, outcome, refs}`). Каждая постная поверхность ДОЛЖНА гарантировать, что терминальный ответ всегда производим. |

Поле `outcome` глагола `answer` — это **строка свободной формы**, допустимые
значения которой определяются собственным контрактом ответа бэкенда; ядро
владеет лишь *формой* поля, но никогда — фиксированным набором значений.

### Чтения, отслеживаемые для grounding

`GROUNDING_TRACKED_TOOLS` — это frozenset `{read}`: только успешные вызовы `read`
фиксируют наблюдённое свидетельство:

```python
GROUNDING_TRACKED_TOOLS: frozenset[str] = frozenset({LEAN_TOOL_READ})
```

Нижестоящий слой grounding/цитирования трактует каждый зафиксированный путь
`read` как наблюдённое свидетельство, так что собственные минимальные чтения
модели становятся её набором цитирований. `read_silent` возвращает идентичное
содержимое, но явно **не** фиксируется. Вынесение этого разделения в контракт
ядра означает, что любой бэкенд реализует одну и ту же дисциплину
чтение-против-просмотра. Корпоративный адаптер может проверять своё поведение
(не)фиксации против этого frozenset.

### Профили и привязка к бэкенду

Ядро владеет лишь *контрактами и именами*; оно не регистрирует ни одного
конкретного `Tool` для постного пула. Вспомогательные функции строят канонические
спецификации и валидируют активный профиль:

- `lean_tool_surface()` → полный пул как спецификации `ToolDefinition` в порядке
  `LEAN_TOOL_NAMES` (стабильном для переиспользования кэша и детерминированных
  тестов).
- `lean_tool_definition(name)` / `is_lean_tool(name)` — спецификация / членство
  для отдельного глагола.
- `select_tool_surface_profile(profile)` — нормализует активный профиль к одному
  из `TOOL_SURFACE_PROFILES` (`"legacy"` | `"lean"`), откатываясь к
  сохраняющему поведение значению `"legacy"` по умолчанию для нераспознанного
  значения.

Увидит ли тенант постный пул или ранее существовавшую типизированную поверхность
бэкенда, управляется `RuntimeConstants.tool_surface_profile` плюс флагами
`tool_surface_*_enabled` на каждый инструмент. Хост привязывает каждое
каноническое имя к конкретному бэкенду. О том, как читаются эти флаги, см.
[`runtime-constants.md`](runtime-constants.md).

## Декоратор `@tool`

`tools/decorator.py` предоставляет лёгкий внутриядерный помощник, превращающий
асинхронную функцию в подкласс `Tool`. Pydantic-овский `TypeAdapter` выводит
JSON-схему параметров из аннотаций типов функции; особый параметр
`context: ToolContext` пропускается. Декорируемый вызываемый объект
**заменяется** сгенерированным подклассом `Tool`.

`tool`, `ToolContext` и `ToolResult` реэкспортируются на верхнем уровне пакета:

```python
from protocore import tool, ToolContext, ToolResult


@tool(name="echo", description="Echo back the input.")
async def echo(context: ToolContext, text: str) -> ToolResult:
    return ToolResult(tool_call_id="...", content=text)
```

Оборачиваемая функция должна быть `async` — иначе `@tool` поднимает `TypeError`.
`echo` теперь является подклассом `Tool`, чей `.definition` несёт `name`,
`description` и схему, построенную из аннотации `text: str`. Постные инструменты
по умолчанию, обеспеченные бэкендом, используют этот декоратор, но живут в
корпоративном пакете; само ядро не регистрирует ни одного постного инструмента
по умолчанию (хотя оно поставляет инструменты поверхности протокола ask-user /
память). Для более богатых или stateful-инструментов
реализуйте ABC `Tool` (`contracts/tools.py`) напрямую.

## Конвейер диспетчеризации

`runtime/tool_dispatch.py` — `ToolDispatcher.dispatch(...)` является **единственной
точкой входа в ядро** для выполнения одного `ToolCall` после того, как LLM
закончила его эмитировать. Диспетчер агностичен к реализации инструмента: он
зависит только от `Tool.invoke`. Он **никогда не поднимает исключение** при
ошибке инструмента — каждый режим отказа транслируется в блок
`tool_result(success=false)`, чтобы модель могла восстановиться на следующем ходу,
а запуск никогда не падал жёстко.

`dispatch()` — это асинхронный генератор, который выдаёт конверты `TurnEvent` и,
последним элементом, `DispatchOutcome`. Жизненный цикл:

1. **Поиск в реестре** — `DispatchErrorKind.unknown_tool`, если имя не
   зарегистрировано.
2. **Валидация схемы** — инвариант ограничения по байтам / JSON-сериализуемости
   на входном словаре (специфичная для инструмента Pydantic-валидация живёт в
   корпоративном адаптере).
3. **Гейт разрешений** — расходится на `ToolPermissionGate.check(...)` (ниже).
   Вердикт `require_approval` поднимает событие `tool_call_pending` и не выдаёт
   результата инструмента; вызывающая сторона переводит цикл в `AWAITING`.
4. **Предусловия** — проверяется DAG `ToolDefinition.preconditions` инструмента
   (ниже); неудовлетворённый инструмент срабатывает накоротко с отказом, когда
   установлен `RuntimeConstants.tool_preconditions_enabled`.
5. **Выполнение** — `tool.invoke(ctx)`, обёрнутый в `asyncio.wait_for` с учётом
   `rc.tool_timeout_seconds`.
6. **Хук `PostToolUse`** — fire-and-await; может переписать вывод.

`DispatchOutcome` (frozen) несёт `success`, `content`, `is_error`,
`error_kind`, `approval_required` / `approval_token`, `ask_user_required` /
`ask_user_payload`, `duration_ms` и набор `metadata`. `DispatchErrorKind` — это
таксономия отказов: `validation | permission | execution | timeout |
rate_limit | unknown_tool | consecutive_error_cap`. Последний — это страховка:
как только серия идущих подряд одинаковых ошибок в рамках запуска превышает
`tool_dispatch_consecutive_error_cap`, диспетчер переписывает отказ в этот вид,
чтобы застрявший цикл завершился вместо сжигания итераций.

Инструмент может прикрепить к поднятому исключению машиночитаемый словарь
`structured_error` (например, `{"finalization_recommended": True, "reason": ...}`);
ветка except в диспетчере прокидывает его на `DispatchOutcome.metadata`, и цикл
поднимает модели подсказку о финализации.

См. раздел [Tool dispatch + gating](architecture.md) о контракте эмиссии
событий.

## Гейт разрешений

`runtime/tool_permission.py` — `ToolPermissionGate.check(...)` запускает
асинхронный конвейер и возвращает **первое не-allow** решение
`ToolPermissionDecision`. Поле `outcome` решения — одно из `allow` / `deny` /
`require_approval`, с опциональным переписанным `modified_input` и
`approval_token`. Каждое решение также фиксирует `PermissionStage`, на котором оно
было достигнуто (для телеметрии).

StrEnum `PermissionStage` именует четыре упорядоченные стадии гейта плюс
no-op-значение по умолчанию:

| Порядок | Стадия (`PermissionStage`) | Что проверяет |
|---|---|---|
| 1 | `whitelist` | `ToolVisibilityPolicy` (и любой сужающий whitelist субагента) должен разрешать имя инструмента — `blocked` всегда запрещает, `visible` (когда непуст) является строгим allow-list. |
| 2 | `safety_policy` | Проверки по классу побочных эффектов через цепочку `IToolSafetyPolicy`. |
| 3 | `rate_limit` | Только хост; базовая линия — no-op `allow`. Скомпонуйте политику бакета на Redis через `register_policy`, чтобы запрещать здесь. |
| 4 | `hook` | Хук `PreToolUse` — финальная, наиболее рычажная стадия; может перевернуть `allow` → `deny` / `require_approval` либо изменить аргументы. Пропускается, когда менеджер хуков не подключён. |
| — | `default` | Значение StrEnum по умолчанию, используемое для неявного `allow`, когда ни одна стадия не возразила. |

Политика безопасности реализует `IToolSafetyPolicy` —
`applies_to(side_effect_class)` плюс `evaluate(tool, arguments, ctx)`. Стек
политик по умолчанию содержит ровно одну политику:

- `ShellSafetyPolicyAdapter` — обёртка вокруг `DefaultShellSafetyPolicy`,
  инспектирующая `arguments['command']` для класса побочных эффектов sandbox.

`HttpDnsAllowlistPolicy` и `WorkspacePathPolicy` предоставлены, но **не** входят
в стек по умолчанию; корпоративные стеки накладывают их во время выполнения через
`register_policy`, что сохраняет API ядра замороженным. Гейт всегда включён. Хук
`PreToolUse` — наиболее рычажный шов для гейта вида LLM-as-policy.

См. раздел [Permission gate](architecture.md) о месте гейта в потоке
диспетчеризации и о карте классов побочных эффектов.

## Трёхслойная эффективная поверхность

`runtime/tool_registry.py` — `ToolRegistry` реализует контракт `IToolRegistry`
(`contracts/tool_registry.py`). Его `compute_effective_surface(...)` — это
фильтр на каждый ход, удерживающий список инструментов LLM маленьким и
релевантным, сохраняя при этом байт-детерминированный порядок. Цикл вызывает его
каждый ход, и он применяет три слоя:

1. **Политика** — применяет `ToolVisibilityPolicy` (allow-list `visible` /
   deny-list `blocked` / всегда включаемые `pinned`), давая видимый набор
   тенанта.
2. **Отсечение** — если `top_k is None` или видимый набор уже `<= top_k`,
   возвращает его отсортированным по имени (никакого извлечения вовсе).
3. **Прогрессивное обнаружение** — иначе ранжирует видимый набор по BM25 по
   недавнему запросу пользователя `query` (`runtime/tool_retrieval.py`), всегда
   включает инструменты `pinned` и оставляет топ-K по оценке.

```python
def compute_effective_surface(
    self,
    tenant_id: str,
    policy: ToolVisibilityPolicy,
    *,
    query: str = "",
    top_k: int | None = None,
) -> Sequence[ToolDefinition]: ...
```

Какой бы слой ни сработал, **финальный порядок всегда по возрастанию имени** —
порядок извлечения управляет *отбором*, но эмитируемый список сортируется по
имени, так что контекст LLM остаётся байт-стабильным, а KV-prefix-кэш переживает
ходы. Порог отсечения — это RC `tool_retrieval_top_k`, передаваемый циклом.

> `runtime/tool_pool.py` (`assemble_tool_pool`) — это параллельный сборщик,
> который **не** подключён к циклу; цикл использует `compute_effective_surface`.
> У него есть вызывающие стороны только в тестах и реэкспорт.

См. раздел
[Tool retrieval / pool / registry / 3-layer surface](architecture.md)
о внутреннем устройстве извлечения.

## Предусловия инструментов

Предусловия обеспечивают **порядок** инструментов: инструмент, требующий
предшествующего наблюдения, маскируется, пока его предусловие не удовлетворено,
так что модель не может, например, изменить запись до прочтения управляющей
политики.

Существуют три системы; они никогда не взаимодействуют:

- **Runtime DAG** — `runtime/tool_preconditions.py` (`check_preconditions`,
  `resolve_precondition`, `record_satisfaction`, `compute_masked_tools`,
  `load_satisfied_set` / `store_satisfied_set`). `preconditions` инструмента
  читаются из его `ToolDefinition`; удовлетворённый набор гоняется туда-обратно
  через набор-помощник движка, так что он переживает снапшот/возобновление. Этот
  слой потребляется в пути диспетчеризации (шаг 4 выше) и гейтится
  `RuntimeConstants.tool_preconditions_enabled` (по умолчанию `False`). Он
  **блокирует** инструмент, который модель уже выбрала.
- **Декларативная спецификация** — `contracts/tool_action_preconditions.py`
  содержит типизированную спецификацию правил со строковой полезной нагрузкой:
  `ToolActionPreconditionSpec` / `ToolActionPreconditionRule` /
  `ToolActionPreconditionPredicate` / `ToolActionPreconditionResult`, с видами
  предикатов `PREDICATE_KIND_ARGS_MATCH`, `PREDICATE_KIND_REF_OBSERVED` и
  `PREDICATE_KIND_DOC_OBSERVED` (собранными в `ALL_PREDICATE_KINDS`). Она нацелена
  на предусловия вида *шаблон аргументов + наблюдённое состояние* (например,
  мутирующий бинарник может выполниться только после того, как в этом запуске был
  наблюдён конкретный документ). Строки `kind` правил forward-совместимы:
  неизвестный вид — это no-op времени выполнения, а не отклоняющая снапшот ошибка
  валидации. Подключена лишь как RC-типы плюс корпоративный вычислитель — никакой
  код цикла ядра не читает спецификацию напрямую. Режим:
  `tool_action_preconditions_mode` (`off | shadow | block`, по умолчанию `off`).
- **Run-level forcer** — `runtime/run_tool_preconditions.py` плюс
  `QueryEngineConfig.tool_preconditions`. Упорядоченный кортеж инструментов,
  которые этот запуск **должен** вызвать, прежде чем агент свободен отвечать;
  пока запись outstanding, цикл ставит `LLMRequest.extra['forced_tool_choice']`.
  Пустой кортеж (значение по умолчанию) — no-op. Это **принуждает** инструмент,
  который модель не выбирала.

См. раздел [Tool preconditions](architecture.md#tool-preconditions-dag--action-spec--run-level-forcer)
о механизме предусловий.

## Расширение поверхности инструментов

- **Добавить инструмент:** реализуйте ABC `Tool` (`contracts/tools.py`) или
  используйте `@tool`; зарегистрируйте получившийся `ToolDefinition` в
  `IToolRegistry`. Для постной поверхности, видимой агенту, перенимайте
  канонические имена из `LEAN_TOOL_NAMES` ради кросс-бэкендного единообразия.
- **Управлять видимостью:** задайте `visible` / `blocked` / `pinned` на
  `ToolVisibilityPolicy`.
- **Добавить проверку безопасности:** реализуйте `IToolSafetyPolicy` и
  зарегистрируйте её через `ToolPermissionGate.register_policy` — она вычисляется
  после значений по умолчанию; гейт ядра остаётся замороженным.
- **Гейтировать по наблюдённому состоянию:** поставьте `ToolActionPreconditionSpec`
  через RC предусловий (его запускает корпоративный вычислитель).

См. [`extending.md`](extending.md) для более широкого руководства «выберите свой
шов» и правила границ импорта.
